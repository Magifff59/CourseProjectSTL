# База-ґрунт-фундамент команд для роботі у терміналі:
- *збирає ВСІ ФАЙЛИ в один exe*
` g++ src/main.cpp src/logger.cpp -o logger_app `

- *запуск проги*
` ./logger_app `

## Команди для роботи з GIT
- *додати файли до змін*
` git add . ` 
*(крапочка вкінці свідчить, що будуть додані УСІ файли в чергу на збереження)*

- *збереження чекпоінтів а.к.а комітів*
` git commit -m "опис того, що зробив" `

- *переглянути історію збережень*
` git log --oneline `

- *ВІДКАТ ДО ОСТАННЬОГО ЧЕКПОІНТУ ВРАЗІ, ЯКЩО ВСЕ ПІДЕ ПО ПИЗДІ*
` git restore . ` 
*(крапочка вкінці означає, що УСІ файли вернуцця до останнього чекпоінту)*

## Структура проєкту на покишо
- ` include/ ` — заголовкові файли (.h)
    - ` logger.h `
- ` src/ ` — вихідний код (.cpp)
    - ` logger.cpp `
    - ` main.cpp `
- ` logger_app.exe ` — готовий застосунок
- ` logs.txt ` — результат роботи лоґеру


шо нада на курсач:

1. фільтрація без урахування регістру (case-insensitivity)

Як це зробити: Перед порівнянням просто тимчасово перетворюємо і повідомлення, і пошукове слово в нижній регістр (lower case).

2. запит в терміналі (інтерактивне меню)

повноцінний консольний застосунок.Коли запускаєш .exe, програма не просто виконує команди й закривається, а входить у цикл while. Вона питає: "Що хочеш зробити? 1 — Статистика, 2 — Пошук, 0 — Вихід". Ти вводиш цифру — вона працює. 

3. автоматизація з лоґами:
Логер як частина іншої програми: Твій клас Logger вставляється в умовний "Онлайн-магазин", і коли там падає оплата, магазин сам викликає logger.addLog().

Читання з файлу: Оскільки твій проект — це "Система управління даними", найлогічніше буде навчити твій логер читати існуючий файл. Наприклад, у тебе є файл raw_logs.txt, де 10 000 рядків. Твоя програма "всмоктує" їх у std::vector, а потім ти через меню робиш пошук/фільтрацію.

Генератор: Можна написати маленьку функцію, яка заповнює вектор випадковими логами для тесту (Random Log Generator).


Твій план на наступний крок:
Зробимо меню: Замість жорстко прописаних команд у main, зробимо цикл, щоб ти міг "клацати" функції прямо в терміналі.

Навчимо програму читати файл: Це закриє твоє питання про "звідки беруться дані". Ми зробимо метод loadFromFile, який заповнить std::vector даними з диска.

Case-insensitive search: Додамо ігнорування регістру, щоб пошук був зручним.

4. Кольоровий вивід у консоль: Щоб ERROR був червоним, WARNING жовтим, а DEBUG сірим. Це виглядає дуже професійно для консольного застосунку.

5. Шаблон проектування Singleton (Сінглтон): Це те, що обожнюють питати на співбесідах. Це коли твій логер існує в програмі в єдиному екземплярі, і до нього можна звернутися з будь-якої частини коду без передачі посилання.

6. Вимірювання часу (Profiling): Оскільки у нас є трасування, ми можемо додати можливість заміряти, скільки мілісекунд виконувалася функція.


Наша майбутня ієрархія (від 0 до 5):
DEBUG: Технічне "сміття". Наприклад: "Змінна x = 5", "Запит до бази відправлено". Вмикається тільки під час розробки.

TRACE: Шлях виконання. "Зайшли у функцію А", "Вийшли з функції А". (Це ми вже круто реалізували).

INFO: Загальні події. "Користувач увійшов", "Програма стартувала".

WARNING: Щось іде не так, але працювати можна. "Мало місця на диску", "Повільний інтернет".

ERROR: Конкретна помилка операції. "Файл не знайдено", "Пароль невірний". Програма живе далі.

FATAL (або CRITICAL): Кінець гри. "Пам'ять переповнена", "База даних знищена". Після такого логу програма зазвичай робить exit().

Коли ми завтра будемо додавати ці рівні, ми можемо зробити фільтр ієрархії.
Наприклад: "Покажи мені логі рівня ERROR і вище". Тоді програма автоматично покаже ERROR та FATAL, але приховає INFO. Це і є справжнє "управління даними", а не просто список.
